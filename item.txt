先做 fallback 而不直接整合 MemorySaver / 完整 create_agent

LangChain API 變動頻繁（1.0.x 內部不同次版也有微差）：直接硬綁 create_agent(...) 與 MemorySaver，若執行環境的 langchain 次版本 API 小變動就會跑不動。PoC 要先能「可靠跑」在沒有完美相容情況下也能 fallback。
依賴與環境問題：要使用 MemorySaver / agent 需要正確安裝並設定 LangChain、相關 model provider（OpenAI key 或其它），若環境沒配置會導致整個 endpoint 失效。PoC 現在能在沒有這些條件下仍提供功能。
設計不確定性：Memory 的儲存層（短期 in-memory / Redis / DB）與一致性、隱私策略、過期與容量管理需要先設計好；若直接套入會留下架構性決策未處理的風險。
逐步交付策略：先做小而完整（可測試）的部分能讓你早期驗證查詢拆窗/合併邏輯，再把更複雜的記憶/agent 功能安全地加入。
